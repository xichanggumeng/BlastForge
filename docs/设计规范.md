# 爆擎 BlastForge Demo 技术设计规范

> **项目定位：** 面向模拟商业会议展示的 AI 原生爆破工程辅助决策 Demo  
> **首期核心：** 爆破参数预测与方案规划、Agentic Workflow、多 Agent 协同、知识引用、人工复核  
> **技术基线：** React + Next.js 全栈架构  
> **模型基线：** DeepSeek-V4-Pro  
> **文档用途：** 作为产品设计、前端开发、服务端开发、AI Agent 开发、数据库设计和代码评审的统一技术参考

---

## 0. 文档说明

### 0.1 当前阶段

爆擎 BlastForge 当前处于 **商业展示 Demo / 技术验证原型** 阶段。

本阶段并不追求一次性实现完整的工程生产系统，而是需要用一个高完成度、强交互、强视觉表达的可运行 Demo，向会议参与者清晰展示以下能力：

1. 爆破工程参数可以被结构化采集、预测和规划；
2. AI 能够理解工程场景并自动拆解复杂任务；
3. 多个专业 Agent 能够协同执行任务；
4. AI 能够调用规则、知识库、计算器和评分工具；
5. 每一步推理依据、知识引用和工具调用均可追踪；
6. 方案能够进行多维对比、风险复核和报告生成；
7. 最终结果必须经过人工确认，AI 不替代专业人员决策；
8. 平台在视觉、动画、交互和代码工程质量上均具备商业展示水准。

### 0.2 本规范的核心取舍

本阶段采用以下优先级：

```text
展示效果
    >
核心业务闭环
    >
Agent 架构表达
    >
代码规范与可扩展性
    >
生产级分布式能力
```

这并不意味着降低代码质量，而是避免在 Demo 阶段投入大量时间建设暂时无法被展示和验证的复杂基础设施。

### 0.3 规范等级

- **必须**：正式代码必须遵循；
- **推荐**：默认采用，偏离时应说明原因；
- **可选**：根据开发时间和演示价值决定；
- **禁止**：不得在正式代码中出现。

# 1. 项目技术目标

## 1.1 展示目标

Demo 必须具备以下可感知特征：

- 现代化、专业化、工业科技感的视觉体系；
- 连贯且有层次的页面动效；
- Agent 执行过程可视化；
- 参数变化与结果变化具备即时反馈；
- 图表、流程图、指标卡和场景视图相互联动；
- 具有可演示的完整业务故事线；
- PC 端为主展示端，Mobile 端具备完整响应式体验；
- 加载、执行、成功、风险、失败等状态均有明确视觉表达；
- 页面不能呈现为传统 CRUD 后台管理系统；
- 代码结构可以作为工程能力展示内容。

## 1.2 业务目标

首期重点形成以下闭环：

```text
创建或选择工程场景
    ↓
录入结构化参数与自然语言说明
    ↓
AI 解析与参数标准化
    ↓
知识库检索与规则检查
    ↓
参数预测与方案规划
    ↓
多方案生成与多指标评价
    ↓
安全复核 Agent 交叉检查
    ↓
人工确认
    ↓
生成结构化报告
```

## 1.3 Agent 展示目标

Agent 体系不得仅存在于代码和后端日志中，必须在用户界面中被清晰展示：

- 当前由哪个 Agent 执行；
- Agent 当前任务；
- 输入和结构化输出；
- 调用了哪些工具；
- 引用了哪些知识片段；
- 每一步消耗时间；
- 当前置信度或状态；
- 哪一步需要人工确认；
- Agent 之间如何传递结果；
- 最终方案如何由多个 Agent 共同形成。

# 2. 项目范围与安全边界

## 2.1 Demo 首期范围

首期实现：

- 展示型项目驾驶舱；
- 爆破工程场景创建；
- 工程条件结构化输入；
- 自然语言补充输入；
- 爆破参数预测与方案规划；
- 推荐方案、备选方案和风险方案；
- 参数敏感性与方案对比可视化；
- Agent 池；
- Agentic Workflow 执行；
- RAG 知识引用；
- Tool Calling；
- 安全复核；
- 人工确认；
- 报告预览与导出；
- Agent 执行记录与审计轨迹。

## 2.2 首期不重点建设

以下内容可以保留架构接口，但不应占用首期主要工期：

- 完整组织与商业计费体系；
- 复杂多租户 SaaS；
- 大规模实时协同编辑；
- 完整移动 App 或小程序；
- 生产级微服务治理；
- 大规模 GIS 平台；
- 真实施工设备控制；
- 完整弱代码 Agent 市场；
- 大规模企业知识治理；
- 高可用集群与跨区域容灾。

## 2.3 工程安全边界

本项目属于 **工程辅助展示系统**。

所有预测值、规划值、评分和报告必须标识其数据来源与使用边界。

必须区分：

```text
演示性预测参数
工程辅助建议
需人工复核参数
禁止直接用于施工的关键参数
```

对于装药量、孔网参数、起爆网络、延期时间、安全距离和施工控制指令等高风险内容：

- 默认不得作为可直接执行的现场指令；
- Demo 中如需呈现，只能使用明确标注的模拟数据、教学数据或脱敏数据；
- 页面必须显示“模拟预测”“仅供方案讨论”“需专业人员复核”等状态；
- 报告必须保留人工确认节点；
- AI 结果不得自动转为“已批准”状态。

# 3. 总体技术架构

## 3.1 首期架构决策

首期采用：

> **Next.js 模块化全栈单体 + PostgreSQL/pgvector + DeepSeek-V4-Pro + 可选 Redis Worker**

```text
┌─────────────────────────────────────────────────────────┐
│                  BlastForge Web Demo                    │
│                  Next.js App Router                     │
│                                                         │
│  展示层       参数工作台      Agent 工作台      报告中心 │
│  React        ECharts         React Flow       Preview  │
├─────────────────────────────────────────────────────────┤
│               Application / Use Cases                   │
│  Scenario  Prediction  Workflow  Review  Report         │
├─────────────────────────────────────────────────────────┤
│                   Agent Runtime                         │
│  Orchestrator / Agents / Tools / Memory / Trace         │
├─────────────────────────────────────────────────────────┤
│                Infrastructure Adapters                  │
│  DeepSeek V4 Pro / PostgreSQL / pgvector / Storage      │
└─────────────────────────────────────────────────────────┘
```

## 3.2 为什么首期不拆分独立 AI 服务

立项书中的长期架构强调业务系统与 AI 服务解耦。首期仍在代码层保留该边界，但运行时先采用 Next.js 全栈架构，原因如下：

- 开发周期更短；
- 前后端类型可以直接共享；
- 流式 AI 交互实现成本更低；
- 单仓库更适合 Demo 快速迭代；
- 部署和会议演示更稳定；
- 避免为尚未验证的流量和组织规模提前拆服务。

AI 模块必须通过独立包和 Adapter 设计，使其后续可以平滑迁移为独立 Node.js Agent Service。

## 3.3 服务拆分触发条件

只有出现以下情况时，才考虑将 Agent Runtime 拆成独立服务：

- Agent 任务需要独立扩缩容；
- AI 调用明显影响 Web 请求稳定性；
- 报告生成或知识解析成为长耗时任务；
- 需要独立部署 Python 计算服务；
- 多个客户端共同复用 Agent API；
- 需要独立的模型路由、限流和成本治理；
- 需要长时间后台任务和任务恢复。

# 4. 技术栈基线

## 4.1 核心技术栈

| 分类 | 技术方案 | 首期用途 |
|---|---|---|
| 全栈框架 | Next.js App Router | 页面、RSC、Route Handler、Server Action |
| UI | React | 交互与组件 |
| 语言 | TypeScript Strict | 全链路类型约束 |
| 包管理 | pnpm Workspace | 工作区和依赖管理 |
| 构建组织 | Turborepo | 应用与共享包任务编排 |
| 样式 | Tailwind CSS | 响应式与设计系统 |
| 组件基础 | shadcn/ui + Radix UI | 高质量基础组件 |
| 动画主库 | Motion | 布局、页面、手势、状态动画 |
| 复杂展示动画 | GSAP，可选 | 首页和关键演示序列 |
| 图标 | Lucide React | 通用图标 |
| 图表 | Apache ECharts | 参数、评分和敏感性图表 |
| 流程图 | React Flow | Agentic Workflow 可视化 |
| 表格 | TanStack Table | 参数、运行记录和结果明细 |
| 客户端请求 | TanStack Query | 动态数据、执行状态与缓存 |
| 本地状态 | Zustand | 工作台交互状态 |
| 表单 | React Hook Form | 参数录入 |
| Schema | Zod | 输入、输出、工具和 Agent 契约 |
| ORM | Drizzle ORM | Schema、查询和迁移 |
| 数据库 | PostgreSQL | 结构化业务数据 |
| 向量检索 | pgvector | Demo RAG 知识库 |
| AI SDK | AI SDK + `@ai-sdk/deepseek` | 模型调用、流式输出、工具调用 |
| 大模型 | `deepseek-v4-pro` | 规划、推理、复核和报告 |
| 队列 | BullMQ + Redis，可选 | 长任务和报告生成 |
| 文件存储 | S3 兼容存储，可选 | 文档和报告 |
| 测试 | Vitest + Playwright | 单元、集成与 E2E |
| 代码质量 | Biome + TypeScript | 格式、Lint 和类型检查 |
| 可观测性 | Sentry + 结构化日志 | 错误和 Agent Trace |

## 4.2 依赖引入原则

必须：

- 每个依赖只承担明确职责；
- 动画以 Motion 为主；
- 图表统一使用 ECharts；
- 工作流统一使用 React Flow；
- AI 调用必须通过统一 Provider Adapter；
- 所有外部输入和模型输出必须经过 Zod；
- 依赖版本必须由 lockfile 固定。

禁止：

- 同时大规模使用多个图表库；
- 同时使用多个全局状态管理库；
- 在组件内部直接调用 DeepSeek API；
- 将 API Key 暴露到浏览器；
- 为单个简单效果引入大型动画框架；
- 直接把模型输出当作可信业务对象。

# 8. 视觉设计规范

## 8.1 视觉定位

推荐关键词：

```text
工业科技
高端工程
数据密度
智能协作
可信分析
克制炫酷
```

避免：

```text
传统政务后台
廉价霓虹赛博朋克
过度拟物
大面积纯黑
卡片堆砌
无意义光效
```

## 8.2 色彩体系

推荐采用“深色工业底 + 高亮能量色”的双主题体系。

基础语义：

| Token | 建议含义 |
|---|---|
| `background` | 深灰蓝或冷黑背景 |
| `surface` | 分层面板 |
| `primary` | BlastForge 品牌能量色 |
| `accent` | 智能计算与数据高亮 |
| `success` | 已完成、低风险 |
| `warning` | 待复核、中风险 |
| `danger` | 拦截、高风险 |
| `muted` | 辅助信息和未激活节点 |

建议品牌色方向：

- 主色：爆破橙 / 琥珀金；
- 辅色：电弧蓝 / 冷青；
- 背景：石墨黑 / 深蓝灰；
- 风险：红橙；
- 安全：青绿。

必须：

- 所有颜色通过 CSS Variables 管理；
- 图表颜色必须与全局语义一致；
- 同一状态在所有页面保持同色；
- 深色主题作为会议展示主主题；
- 保留浅色主题以证明设计系统完整性。

## 8.3 字体与排版

必须：

- 中文正文优先使用现代无衬线字体栈；
- 数字指标使用等宽数字特性；
- 页面标题、模块标题、标签和说明形成明确层级；
- 关键参数数值必须高于标签视觉权重；
- 长段说明控制行宽；
- 图表轴、Tooltip 和卡片文字保持统一字号体系。

## 8.4 面板与材质

推荐：

- 半透明表面仅用于局部层级；
- 使用细边框、柔和阴影和低强度高光；
- 关键工作区允许轻微玻璃质感；
- 卡片圆角、边框和阴影统一；
- 不得所有卡片都使用相同视觉权重。

用于：

用于：

用于：

- 首页 Hero；
- 产品能力介绍；
- Demo 开场；
- 报告生成完成。

建议时长：`400ms – 1200ms`

## 9.2 必须实现的关键动画

- 页面进入和布局切换；
- 参数卡片增删；
- 表单步骤推进；
- Agent 节点执行脉冲；
- 工作流连线数据流；
- Tool 调用弹出与回收；
- 知识引用命中动画；
- 图表渐进绘制；
- 方案卡片排序变化；
- 数值递增；
- 风险标记显现；
- 人工确认状态变化；
- 报告生成进度；
- 完成时的克制反馈动画。

## 9.3 动画限制

必须：

- 优先使用 `transform` 和 `opacity`；
- 支持 `prefers-reduced-motion`；
- 动画状态与真实任务状态一致；
- 页面离开时清理时间轴和监听器；
- 移动端降低粒子和背景动画强度；
- Agent 执行时不得阻塞页面其他操作。

禁止：

- 所有元素同时入场；
- 无限循环大面积粒子；
- 每次 Hover 都产生明显弹跳；
- 为等待模型返回制造无法跳过的假动画；
- 使用动画掩盖真实错误；
- 在图表中使用过多颜色和特效。

# 14. Agent 架构体系

## 14.1 Agent Runtime 组成

```text
Agent Runtime
├─ Orchestrator
├─ Agent Registry
├─ Workflow Engine
├─ Tool Registry
├─ Context Builder
├─ Memory Store
├─ Guardrails
├─ Human Approval
└─ Trace Recorder
```

## 14.2 核心 Agent

### 1. Supervisor Agent

职责：

- 理解用户目标；
- 选择 Workflow；
- 分配 Agent；
- 控制步骤；
- 处理重试和中止；
- 汇总最终结果。

禁止直接承担全部专业工作。

### 2. Input Normalizer Agent

职责：

- 解析自然语言输入；
- 提取工程类型、地质、水文、环境和成本约束；
- 识别缺失参数；
- 输出标准参数对象；
- 请求用户补充必要信息。

### 3. Knowledge Retriever Agent

职责：

- 构造检索查询；
- 调用混合检索工具；
- 返回知识片段和引用；
- 对来源进行分类；
- 去除低相关结果。

### 4. Parameter Planner Agent

职责：

- 根据标准化输入和知识依据进行参数预测与规划；
- 输出建议区间、方案假设和影响因素；
- 标记高敏感参数；
- 不直接批准任何施工参数。

### 5. Scheme Generator Agent

职责：

- 生成推荐、备选和风险方案；
- 保证方案结构一致；
- 给出适用条件和限制；
- 将规划结果转换为可比较方案。

### 6. Evaluation Agent

职责：

- 调用确定性评分工具；
- 按安全性、适用性、经济性、施工便利性和环境影响评分；
- 输出排序和评分依据；
- 不得仅依靠语言模型主观打分。

### 7. Safety Reviewer Agent

职责：

- 检查约束冲突；
- 识别缺失参数；
- 验证引用和规则；
- 标记高风险内容；
- 生成“人工重点确认清单”；
- 必要时阻断 Workflow。

### 8. Report Agent

职责：

- 汇总最终方案；
- 生成结构化报告；
- 关联引用和 Agent Trace；
- 输出可预览文档；
- 不得隐藏风险和未确认项。

## 14.3 Agent 定义规范

每个 Agent 必须声明：

```ts
interface AgentDefinition<TInput, TOutput> {
  id: string
  name: string
  description: string
  model: string
  mode: 'thinking' | 'non-thinking'
  inputSchema: ZodType<TInput>
  outputSchema: ZodType<TOutput>
  tools: string[]
  maxSteps: number
  timeoutMs: number
  systemPromptVersion: string
  requiresApproval: boolean
}
```

## 14.4 Agent 设计原则

必须：

- 一个 Agent 只承担明确职责；
- Agent 输入输出具备 Schema；
- Prompt 版本化；
- Tool 白名单化；
- Agent 运行可追踪；
- 关键结论必须带来源；
- 高风险步骤必须经过安全复核；
- Workflow 必须可暂停、恢复和人工介入。

禁止：

- 使用一个超级 Agent 完成全部任务；
- Agent 之间传递无结构长文本；
- 让模型自行决定所有安全规则；
- 无限制递归调用；
- Agent 自动修改已批准结果；
- 将模型隐藏思维过程直接展示给用户。

# 33. 核心开发原则

1. **Demo 不是静态原型，必须具备真实可运行的核心闭环。**
2. **页面不是传统后台，核心任务必须以工作台和可视化方式呈现。**
3. **Agent 架构必须可见、可解释、可追踪。**
4. **DeepSeek-V4-Pro 通过统一 Provider 接入，不得与业务代码耦合。**
5. **大模型负责理解、规划和生成，确定性代码负责校验、计算和约束。**
6. **所有核心模型输出必须经过 Zod 校验。**
7. **所有关键结论必须关联知识依据或明确标识为模型推断。**
8. **高风险参数必须经过规则检查、安全 Agent 和人工复核。**
9. **动画服务于任务状态、空间关系和会议叙事，不制造视觉噪音。**
10. **图表必须帮助用户理解方案，而不是只展示技术效果。**
11. **PC 展示效果优先，同时保证 Mobile 主流程完整。**
12. **会议 Demo 必须具备预设场景、回放数据和模型故障降级。**
13. **代码、Schema、Prompt、Workflow 和 Agent Definition 都是项目展示成果。**
14. **先完成一个令人信服的参数规划与 Agent 协作闭环，再扩展平台功能。**
